# Onezae Health — Detailed Project Documentation

This document describes the current repository implementation in enough detail to support product development, onboarding, maintenance, and future planning. It is written from the code and configuration present in this repository; it does not imply that optional integrations are enabled in a live environment.

Related documentation: [Project Overview](PROJECT_OVERVIEW.md) · [Architecture](ARCHITECTURE.md) · [Setup and operations](../README.md)

## 1. Product scope

Onezae Health is a hospital / clinic web application for patient access, appointment coordination, doctor workflows, and basic administrative management. Its central workflow is: a patient finds a doctor, chooses a free scheduled slot, books an appointment, communicates with the care team, and later reviews visit information and prescriptions. Doctors manage their appointments and care relationship; administrators configure the clinic and staff.

The system has three roles:

| Role | Account creation | Main application area |
| --- | --- | --- |
| `PATIENT` | Public patient registration | `/patient` |
| `DOCTOR` | Created by an administrator | `/doctor` |
| `ADMIN` | Created through backend administrative tooling | `/admin` |

The frontend has patient, doctor, and admin route groups with role guards. The API is authoritative: UI guards improve navigation but do not replace server side authorization.

### Patient capabilities

- Create an account, sign in, manage profile/contact details, and upload/remove an avatar.
- Search active doctors by name or specialization and view public profiles.
- Inspect a doctor's date availability and specific slots.
- Book, view, and cancel appointments subject to policy.
- Exchange text and image messages with a doctor where the care relationship is authorized.
- See notifications, unread counts, completed visit history, prescriptions, and active medication information.
- Request prescription-related follow-up using prescription request endpoints.
- Use the symptom assistant for general guidance and live doctor/availability lookup, with direct booking of a selected slot in the assistant flow.

### Doctor capabilities

- View own profile and schedule, patient list, and patients associated with the doctor's appointments.
- Update own professional bio and qualifications; account name, phone, and avatar are managed through user profile endpoints.
- View and transition assigned appointments (confirm, complete, no-show, cancel as allowed).
- Communicate with associated patients.
- Create, update, list, and delete prescriptions subject to ownership rules; fulfill prescription requests.

### Administrator capabilities

- Create, update, activate/deactivate, and manage doctor accounts and specializations.
- Manage schedules, shifts, leave, clinic-wide closures/holidays, and time off.
- Review and manage users and appointments, dashboard summaries, and audit history.
- Administrative functionality is under `/api/v1/admin`; exact operations are defined in `backend/app/api/v1/routes/admin.py` and schemas/services.

## 2. System design

```text
Frontend SPA (React + TypeScript)
  ├─ REST API client (Axios; /api/v1)
  ├─ access token in memory; refresh cookie sent automatically
  └─ WebSocket client for realtime events/chat
              │
              ▼
FastAPI application (Python modular monolith)
  ├─ API routers → Pydantic validation → auth/RBAC dependencies
  ├─ domain services and transaction rules
  ├─ AI assistant/tool registry → Groq (optional)
  ├─ storage adapter → Cloudinary (optional)
  ├─ email adapter → console or disabled currently
  └─ SQLAlchemy async session
              │
              ▼
MySQL 8 (intended production database) / SQLite (local and tests)
```

### Request path

1. A browser route renders a role appropriate page. Feature modules use API clients under `frontend/src/features/`.
2. Axios sends requests to `VITE_API_BASE_URL`, default `/api/v1`, with credentials. If the in-memory access token expires, the client attempts a refresh using the httpOnly cookie and retries the request once.
3. FastAPI route dependencies parse the authenticated user, role, database session, and applicable rate limit.
4. Pydantic request schemas validate input. Route handlers delegate business rules to a service module.
5. SQLAlchemy persists the operation; notifications and audit events are generated by the relevant workflows.
6. The response schema controls what data is exposed. Realtime events may be sent to connected users.

## 3. API reference by feature

All application routes are prefixed by `/api/v1` by default (`API_V1_PREFIX`). OpenAPI/Swagger is enabled outside production at `/docs`; the OpenAPI JSON is under `/api/v1/openapi.json`. Exact request/response fields live in `backend/app/schemas/`.

| Area | Routes / operations | Access and purpose |
| --- | --- | --- |
| Health | `GET /health`, `GET /health/ready` | Liveness and database readiness. |
| Metadata | `GET /meta` | Public runtime metadata for the client. |
| Authentication | `POST /auth/register`, `/login`, `/refresh`, `/logout`, `/change-password`, `/forgot-password`, `/reset-password` | Patient self-registration; patient/staff portal login; refresh rotation; logout; password lifecycle. Auth requests are rate limited. |
| User | `GET /users/me`, `PATCH /users/me`, `POST /users/me/avatar`, `DELETE /users/me/avatar` | Current user and own profile/avatar. Temporary-password users can read profile while being restricted from other normal operations. |
| Directory | `GET /specializations`, `GET /doctors`, `GET /doctors/{doctor_id}` | Authenticated users browse active specialties and doctors; doctor listing supports search and specialization filter. |
| Availability | `GET /doctors/{doctor_id}/slots?date=...`, `GET /doctors/{doctor_id}/availability?from=...&days=...` | Returns slot detail or free slot counts in the clinic timezone; slot timestamps are UTC. |
| Appointments | `POST /appointments`, `GET /appointments`, `GET /appointments/{id}`, `POST /appointments/{id}/cancel`, `/confirm`, `/complete`, `/no-show` | Bookings, scoped lists, details, and state transitions. Query filters include status, date range, doctor/patient, and scope where role permits. |
| Doctor portal | `GET/PATCH /doctor/me`, `GET /doctor/schedule`, `GET /doctor/patients`, `GET /doctor/patients/{patient_id}` | Doctor self-service and own patient access. Patient detail requires an appointment relationship. |
| Chat | `GET/POST /chat/conversations`, `GET /chat/conversations/{id}/messages`, `POST /chat/conversations/{id}/messages`, `/images`, `/read`, `GET /chat/unread-count` | Doctor/patient communication. Message history uses cursor parameters (`before_id`, `after_id`); text sends support client idempotency IDs. |
| Realtime | WebSocket `/api/v1/ws` | Authenticated realtime messages and notifications; see `backend/app/api/v1/routes/ws.py` and `frontend/src/lib/realtime.ts`. |
| Notifications | `GET /notifications`, `/unread-count`, `POST /notifications/{id}/read`, `/read-all` | Current user's notification feed/read status. |
| Records | `GET /records/visits` | Completed visit history for the signed-in patient. |
| Prescriptions | `POST/GET /prescriptions/requests`, `POST /prescriptions/requests/{id}/fulfill`, `POST/GET /prescriptions`, `GET /prescriptions/{id}`, `GET /prescriptions/appointment/{appointment_id}`, `PUT/DELETE /prescriptions/{id}` | Prescription requests and structured prescription lifecycle with role/ownership filtering. |
| AI assistant | `GET/POST /ai/conversations`, `GET/POST /ai/conversations/{id}/messages`, `POST /ai/conversations/{id}/book`, conversation deletion endpoint | Patient symptom assistant, history, tool-assisted doctor/slot lookup, and booking. AI message endpoint is rate limited. |
| Admin | `/admin/...` | Doctor, specialization, schedule, time-off, clinic closure, appointment/user management, dashboard and audit operations. Consult the route module and schemas for endpoint-by-endpoint fields. |

The list is a navigation aid, not a replacement for the OpenAPI spec. Always consult route decorators and response/request schemas before integrating a new client.

## 4. Domain model and relationships

| Entity / table group | Purpose and important relationships |
| --- | --- |
| `users` | Common identity, credentials, role, active/deleted flags, password-change flag, token version, and avatar metadata. A user can have a patient or doctor profile. |
| `patients` | Patient-specific date of birth, gender, and emergency contact. One-to-one with a user. |
| `doctors` | Qualification, experience, bio, and specializations. One-to-one with a user. |
| `specializations`, `doctor_specializations` | Searchable specialty directory and doctor-to-specialty many-to-many relation. |
| `doctor_schedules` | Weekly clinic-local working periods. Multiple rows per weekday represent shifts; effective dates support temporary schedules. |
| `doctor_time_off` | Doctor leave/unavailability or clinic-wide blocks (`doctor_id` null). Stored as UTC instants. |
| `appointments` | Patient/doctor booking, start/end, status, reason, notes, cancellation/confirmation/completion metadata, and reminder state. |
| `prescriptions`, prescription items / requests | Doctor-authored prescription and medication details, and patient requests. See prescription model/schema files for exact fields. |
| `conversations`, `messages`, `message_attachments` | One doctor-patient thread per pair; text/image message metadata and read markers. Image bytes live in Cloudinary, not the database. |
| `ai_conversations`, `ai_messages` | Patient assistant threads and messages, including structured result/tool/model metadata. |
| `notifications` | User-facing notification and read/deduplication state. |
| `audit_logs` | Append-only record of selected sensitive/business actions, actor, entity, request context, and details. |

Identity credentials are separate from patient/doctor profile data. Clinical history should not be hard-deleted as a side effect of account deactivation. Use migration files as the authoritative database schema history.

## 5. Core workflows and business rules

### Appointment discovery and booking

1. Doctor schedules define recurring weekday intervals in clinic-local wall-clock time; several intervals can represent a split shift.
2. Effective date limits and time off/clinic closures are applied when generating daily slots.
3. Slots are converted to UTC for API use and persistence. Nonexistent daylight-saving times are skipped; ambiguous times resolve to the first occurrence.
4. Booking must match an available generated slot and satisfy configured lead-time and booking-window rules.
5. The application checks availability for a helpful error, but database generated-column unique indexes are the final concurrency protection. A race becomes a conflict response (`409 slot_unavailable`).
6. The patient and doctor cannot hold the same active slot twice. Only `BOOKED` and `CONFIRMED` appointments occupy a slot; cancelled/completed/no-show states release it.

### Appointment state transitions

Common transitions are `BOOKED → CONFIRMED → COMPLETED`, `CONFIRMED → NO_SHOW`, and cancellation from permitted pre-terminal states. Patients may cancel their own appointment only before the configured cutoff; doctors/admins have additional actions. The backend computes allowed actions and enforces transitions; never make the browser the source of truth.

Changing doctor schedules/time off does not silently erase existing bookings. Conflicts are surfaced for administrative handling.

### Chat and read state

- A conversation is between one doctor and one patient; opening it requires a valid care relationship (an appointment exists).
- Read access is scoped to the two participants. Admins do not receive conversation access through the chat API.
- Messages support retry idempotency by client ID. History is cursor-paginated.
- Read receipts use per-side last-read message identifiers; unread notifications are deduplicated for an unread streak.
- Image attachments are content-sniffed and size-limited. Chat assets use Cloudinary authenticated delivery; storage records identifiers/metadata and returns signed access URLs.

### Prescription and patient record access

Doctors author prescriptions. Patient reads are limited to the patient's own prescriptions; doctors to prescriptions they issued; admin queries are role governed. Patient visit history is derived from completed appointments and includes doctor/specialty and available clinical notes. Do not widen these scopes without a privacy review.

## 6. AI assistant details

### Provider and model

- The server uses the Groq SDK (`AsyncGroq`) for chat completions and tool calling.
- The configured model name is `openai/gpt-oss-120b`, controlled by `GROQ_MODEL`. The model identifier is passed to Groq; this code does not call OpenAI's API.
- `GROQ_API_KEY` is a backend-only secret. The frontend calls Onezae's API, never the LLM provider directly.
- A provider abstraction (`LLMClient`) allows fake clients in tests and replacement of the provider implementation.

### Agent and data access

The agent has a bounded loop, timeout and token/iteration budgets. Tool arguments are schema validated. Available tools are implemented under `backend/app/ai/tools/` and cover active specializations, doctor search/profile, availability, and bookable slots. Tools use domain services and return public directory/availability data; they do not give the model arbitrary SQL access. A structured response is validated before persistence. Tool-derived doctor IDs and known specialty names are used to filter model suggestions.

The assistant can look up real hospital data, but the current design is not document RAG: there is no vector database or indexed clinical knowledge corpus configured. “Retrieval” refers to live structured application data exposed through tools.

### Safety and failure behavior

- The assistant provides informational symptom guidance, not diagnosis or treatment.
- Red-flag patterns can force an emergency urgency and fixed emergency message. Emergency number is configurable (`EMERGENCY_PHONE_NUMBER`, default `112`).
- The server applies a fixed disclaimer, rejects invented doctor references, normalizes specialties, and removes unverified medication dosages.
- If the provider key is missing, general model answers may return unavailable; retrieval-only results and emergency fallback behavior may still operate for supported cases.
- Provider errors/timeouts can result in a safe fallback. The behavior is documented in `backend/app/ai/service.py` and `safety.py`; maintain it with tests when changing prompts/tools/provider code.
- The application's red-flag rules are not a substitute for clinical triage, and pattern matching cannot guarantee detection of every emergency.

Configured AI environment variables: `GROQ_API_KEY`, `GROQ_MODEL`, `AI_TEMPERATURE`, `AI_MAX_ITERATIONS`, `AI_MAX_TOKENS`, `AI_TIMEOUT_SECONDS`, `AI_MAX_RECOMMENDED_DOCTORS`, and `EMERGENCY_PHONE_NUMBER`. Input/history bounds are also defined in settings.

## 8. Authentication, authorization, and security controls

- Passwords are bcrypt hashed. Password schema rules and maximum byte length are defined in auth schemas/services.
- Short-lived access JWTs are held only in browser memory. Refresh tokens use a rotating httpOnly cookie scoped to `/api/v1/auth`; cookie security/same-site behavior is configurable.
- The server rechecks role and account status from the database rather than trusting the JWT role claim. `token_version` invalidates outstanding tokens after sensitive account actions.
- Admin-issued temporary credentials can require password change; guarded requests are restricted until the user changes the password.
- Password reset responses avoid disclosing whether an account exists; reset token is single use through token-version invalidation and reset links use URL fragments.
- Role dependencies and service ownership checks protect resources. Inaccessible resource lookups may return `404` to avoid confirming that the resource exists.
- Rate limits cover authentication, AI, and uploads. Configuration can enable/disable rate limiting and tune limits.
- Request context middleware and structured logging attach request IDs. Avoid logging credentials, reset tokens, full patient message content, or unnecessary health details.
- Production settings reject insecure secret/debug/cookie/CORS combinations. Configure explicit trusted origins/hosts and HTTPS at the reverse proxy.

These controls are implementation mechanisms, not a compliance certification. Before handling real patient data, assess deployment security, access policy, encryption/backups, breach response, retention, consent, vendor agreements, and applicable law.

## 10. Database and migration strategy

- MySQL 8 with InnoDB and `utf8mb4` is the intended deployment database. SQLite is the fallback for simple local use and isolated test databases; database-specific constraints must be checked for compatibility.
- SQLAlchemy uses async sessions/drivers (`aiomysql` for MySQL; `aiosqlite` for SQLite).
- Persisted instants use UTC-aware application helpers and a custom datetime type; schedule working hours are clinic-local wall-clock values.
- Schema evolution is managed in `backend/alembic/versions/`. Every model schema change requires a reviewed migration. Apply migrations during release before starting new code.
- Double-booking uniqueness depends on MySQL generated columns and unique indexes. Treat this as a correctness invariant.
- Production deployment should use encrypted backups and a tested restore process. The repository does not configure backups or a managed database service.

## 11. Notifications, reminders, and realtime operations

Notifications are persisted and may be pushed in realtime and handed to the email abstraction. Notification deduplication keys are used to avoid repeated notices for equivalent events. The reminder script (`python -m scripts.send_reminders`) is intended to be scheduled periodically by an external scheduler; the code repository does not install a scheduler. Email sends are not truly delivered until a production email adapter is implemented.

The realtime connection manager is process-local. For multi-worker serving, messages sent from one worker may not reach clients connected to another worker. The current deployment documentation recommends one worker or a future shared broker integration. The frontend reconnect/catch-up behavior and message cursor APIs are relevant to realtime reliability.

## 13. Local development and release operations

### Local prerequisites

- Python 3.12 or later.
- Node.js 20.19 or later (the root README recommends Node 22 LTS).
- MySQL 8 for parity with intended deployment; SQLite is suitable for a quick local start.
- Optional Groq and Cloudinary credentials for AI model generation and image upload.

### Standard backend lifecycle

1. Create/activate `backend/.venv` and install `backend/requirements.txt`.
2. Copy and edit `backend/.env.example` as `backend/.env`.
3. Initialize the configured database as needed, then run Alembic migrations.
4. Seed development defaults only for local use; create production administrators using the dedicated script and strong unique credentials.
5. Run the ASGI application with Uvicorn locally. Production Linux example in README uses Gunicorn with the provided config.

### Standard frontend lifecycle

1. Install dependencies in `frontend/` using the lockfile (`npm ci` for reproducible installs).
2. Configure public `VITE_*` settings in `.env.local` if defaults are not appropriate.
3. Run Vite for local development; create a static production build with `npm run build`.

The root README contains exact commands and platform-specific notes. Keep migrations, backend release, frontend build, reverse proxy, TLS, and reminder scheduling in the deployment runbook used by the operator.

### Quality tooling present

- Backend: Ruff lint/format, mypy, pytest.
- Frontend: ESLint, Prettier, TypeScript typecheck, Vitest, production build.
- Tests exist for authentication, users, admin, scheduling, appointments, doctors, chat, notifications, prescriptions, AI, and compatibility/health cases.

This document change did not execute the test suites.

## 14. Known gaps and decisions for future work

1. **Hosting:** Choose and document a deployment provider, network topology, TLS termination, secrets management, and monitoring. Current files only offer general nginx/Gunicorn or Windows hosting patterns.
2. **Email delivery:** Implement and test a real provider, delivery retries, bounce handling, and secure template management before expecting password reset/reminder email to reach end users.
3. **Realtime scaling:** Add Redis/pub-sub or another shared transport before increasing backend worker count.
4. **AI data governance:** Decide whether sending symptom text to Groq is acceptable for the target deployment; assess provider terms, retention, consent, and jurisdiction before real patient data is used.
5. **Clinical governance:** Validate emergency patterns and all user-facing medical copy with qualified clinical stakeholders; define escalation, review, and incident processes.
6. **Observability:** Define production metrics, tracing, alerting, audit retention, log redaction, and operational ownership.
7. **Data lifecycle:** Document retention/deletion/export policies, backup encryption, restore objectives, and access review processes.
8. **Compliance:** Confirm required privacy, security, and healthcare regulations based on the actual operating location and organization. The code alone cannot determine compliance status.

When one of these decisions is implemented, update this document, the overview, architecture notes, environment examples, and deployment instructions together.
